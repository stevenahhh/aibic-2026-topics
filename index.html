풀어야 할 문제

  1. 표·서식이 섞인 교재의 청킹과 검색. 교재에는 "도표, 서식 구조 등 다양한 형식의 자료"가 있고, "청킹 방식과 검색 전략은 참가자 자율 설계"입니다(슬라이드 @500s). 이 지점에서 팀마다 차이가 납니다.
  2. 청크 안에서만 답하고 근거를 인용하기. "검색된 교육 자료 청크 내에서만 답변 생성, 근거 문서·단원 출처 명시"(슬라이드 @60s). 검색 결과가 절반만 맞아도 모델이 빈 부분을 지어내기 쉽습니다.
  3. 정답을 숨기는 튜터링. 수준 확인 → 학습 목표 → 단계별 힌트 → 퀴즈로 이어지는 멀티턴 대화가 필요합니다 05:02~05:47. 단일 프롬프트로는 상태에 따라 힌트 강도를 조절하기 어렵습니다.
  4. 범위 이탈과 유해 요청 방어. 공격 쿼리 세트에는 "범위 이탈 요청, 유해·민감 요청, 탈옥·우회 프롬프트"와 "정상 질문처럼 교묘하게 위장한 케이스"가 들어 있습니다(슬라이드 @500s).
  5. 가장 어려운 문제는 정확성과 안전성의 트레이드오프입니다. 발표자는 "트레이드 오프가 있는데, 아마 이거를 푸는 것이 이번 주제를 선택하시는 분들에 있어서 가장 재미있게" 풀 수 있는 부분이라고 했습니다 07:13~07:25. 막는 쪽을 강화하면 정상 질문까지 거절하고(과잉 거절), 방어를 약하게 하면 위장 공격이 통과합니다.

우승 설계 제안

  • 구조는 입력 레일(의도 분류) → 하이브리드 검색(표는 마크다운 표와 요약행을 함께 인덱싱) → 스캐폴딩 정책을 가진 튜터 → 출력 레일(주장 단위 근거 검증, 유해성, 인용 검증) → 거절 템플릿 순서입니다. 거절 템플릿은 「그건 범위 밖이지만 교재 ○단원을 보세요」처럼 교재로 되돌립니다.
  • 핵심 결정은 최종 안전 판정을 출력 레일의 근거 검증에 두는 것입니다. 그러면 입력 레일을 느슨하게 둘 수 있어 과잉 거절이 줄어듭니다. 트레이드오프를 구조로 푸는 방식입니다.
  • 다른 7팀과의 차이는 세 가지입니다. ① 가드레일 강도별 안전성-유용성 파레토 곡선, ② 제공 세트에 없는 한국어 위장 공격과 교재 속 간접 프롬프트 인젝션을 직접 만든 레드팀 세트, ③ 거절 대신 교재로 되돌리는 응답.
  • 모델은 ML API에서 생성용 대형 모델 하나와 분류·검증용 소형 모델을 나눠 씁니다. Helpy Code가 작업 크기에 따라 큰 모델과 작은 모델을 섞는다는 엘리스 설명 02:48~03:07과 취지가 같아 심사위원에게 설명하기 좋습니다.
  • 리스크: 데이터 스키마가 바뀔 수 있습니다. Helpy Code를 학생이 어떤 형태로 쓰는지도 아직 모릅니다. 한국어 안전 분류 품질도 변수입니다. 그래서 평가 하네스를 2주 차에 먼저 만들고, 변경할 때마다 다시 측정합니다.

  • AWS: 채용공고 수백 건을 라벨링하고 추출 정확도를 재는 데이터·백엔드 작업이 팀의 강점인가? 화려한 화면 없이 근거 사슬로 설득할 수 있는가?
